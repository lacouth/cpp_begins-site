    9. Destrutor, RAII e a regra do zero¶

    Sem vídeo correspondente

    Este é o capítulo mais importante do curso, e a playlist atual não tem um vídeo dedicado a ele. Leia com atenção — o assunto aqui é o motivo pelo qual a Unidade 5 (filas, pilhas, listas encadeadas) não vaza memória, e é o alicerce de praticamente todo código C++ de produção.

    O problema: quem libera o que foi alocado?¶

    Em C, alocar memória dinamicamente e esquecer de liberar é o bug mais clássico que existe:

    Pessoa* p = malloc(sizeof(Pessoa));
p->nome = malloc(50);
strcpy(p->nome, "Ana");
// ... uso de p ...
// esqueceu o free(p->nome) e o free(p) -- vazamento de memoria

    Cada malloc precisa de um free correspondente, e é responsabilidade sua, humana, lembrar disso em todo caminho possível do código — inclusive quando uma função retorna cedo por causa de um erro, ou lança uma exceção no meio do caminho. É fácil esquecer, e o compilador não ajuda em nada.

    new e delete: o equivalente C++ de malloc/free¶

    C++ tem new/delete, parecidos com malloc/free, mas que também chamam construtor/destrutor (mais sobre destrutor já já):

    Pessoa* p = new Pessoa();   // aloca e constroi
delete p;                    // destroi e libera

    Só que new/delete têm exatamente o mesmo problema de fundo que malloc/free: você ainda precisa lembrar de chamar delete, e ainda é fácil esquecer. C++ tem uma saída melhor — e é a ideia central deste capítulo.

    Destrutor: o método que roda quando o objeto morre¶

    Assim como um construtor é chamado automaticamente quando um objeto nasce, um destrutor é chamado automaticamente quando um objeto morre — seja porque saiu de escopo (variável local que chegou ao fim do bloco {}), seja porque foi explicitamente destruído com delete.

    Sintaxe: ~NomeDaClasse(), sem argumentos, sem tipo de retorno:

    class Arquivo {
private:
    FILE* ponteiro_;

public:
    Arquivo(const std::string& caminho) {
        ponteiro_ = fopen(caminho.c_str(), "r");
        std::cout << "abrindo arquivo\n";
    }

    ~Arquivo() {
        if (ponteiro_ != nullptr) {
            fclose(ponteiro_);
        }
        std::cout << "fechando arquivo\n";
    }
};

void processa() {
    Arquivo a("dados.txt");
    // ... usa a ...
}   // "a" sai de escopo aqui -- o destrutor ~Arquivo() roda AUTOMATICAMENTE

    Ao sair de processa(), a deixa de existir, e ~Arquivo() é chamado sem que você precise escrever nada para isso acontecer. Não importa como a função termina — return normal, return antecipado, ou (você vai ver na próxima seção do curso) uma exceção lançada no meio — o destrutor sempre roda para todo objeto local que estava vivo naquele escopo. Essa garantia é o que torna o padrão a seguir tão poderoso.

    RAII: Resource Acquisition Is Initialization¶

    A ideia central do capítulo, resumida numa frase: um recurso (memória, arquivo, conexão de rede, mutex) deve ser amarrado ao ciclo de vida de um objeto. O construtor adquire o recurso; o destrutor o libera. Enquanto o objeto existir, o recurso existe; quando o objeto morre — de qualquer jeito que seja —, o recurso é liberado automaticamente.

    Você já usou RAII sem perceber: std::string e std::vector são exemplos de RAII. std::vector<int> v aloca memória internamente conforme cresce (no construtor e em cada push_back que precisa de mais espaço) e libera tudo automaticamente no destrutor, quando v sai de escopo — é por isso que você nunca precisou dar delete em nada ao usar vector desde a Unidade 2. std::ofstream/std::ifstream, do capítulo 7, também: o arquivo fecha sozinho porque o destrutor do stream fecha.

    Vamos escrever nossa própria classe RAII, envolvendo um recurso alocado com new:

    class Buffer {
private:
    int* dados_;
    std::size_t tamanho_;

public:
    explicit Buffer(std::size_t tamanho)
        : dados_(new int[tamanho]), tamanho_(tamanho) {
        for (std::size_t i = 0; i < tamanho_; i++) {
            dados_[i] = 0;
        }
    }

    ~Buffer() {
        delete[] dados_;   // delete[] porque foi alocado com new[]
    }

    void define(std::size_t indice, int valor) {
        dados_[indice] = valor;
    }

    int obtem(std::size_t indice) const {
        return dados_[indice];
    }

    std::size_t tamanho() const {
        return tamanho_;
    }
};

void usa_buffer() {
    Buffer b(100);
    b.define(0, 42);
    // ... usa b ...
}   // ~Buffer() roda aqui -- delete[] dados_ acontece sozinho, sem voce escrever nada

    Note delete[] (com colchetes), não delete: memória alocada com new T[n] precisa ser liberada com delete[], e memória alocada com new T (um objeto só) precisa de delete sem colchetes. Misturar os dois é comportamento indefinido.

    O problema da cópia (por que a "regra do zero" existe)¶

    Existe uma armadilha séria com a classe Buffer acima: o que acontece se você copiar um Buffer?

    Buffer a(10);
Buffer b = a;   // copia "rasa": b.dados_ aponta PARA O MESMO array que a.dados_

    Sem você escrever nada a mais, C++ gera um construtor de cópia padrão, que copia cada campo individualmente — inclusive o ponteiro dados_. Resultado: a e b acabam apontando para o mesmo bloco de memória. Quando b sai de escopo primeiro, ~Buffer() roda e dá delete[] naquele bloco. Quando a sai de escopo depois, ~Buffer() roda de novo e tenta delete[] no mesmo bloco, que já foi liberado — double free, comportamento indefinido, e um dos bugs mais dolorosos de C++ de encontrar.

    Isso é o motivo de existir a chamada regra dos 3: se uma classe precisa de destrutor customizado (porque gerencia um recurso manualmente), ela também precisa de construtor de cópia e operador de atribuição de cópia customizados — os três andam juntos, porque o problema acima (cópia rasa de um recurso que só pode ter um dono) afeta os três.

    A regra do zero: a saída recomendada¶

    A regra dos 3 (ou dos 5, contando move semantics, fora do escopo deste curso) resolve o problema, mas dá trabalho e é fácil de errar. A recomendação moderna, e a que este curso adota, é mais simples: na dúvida, regra do zero.

    Nunca gerencie um recurso bruto (new/delete) diretamente dentro da sua classe. Em vez disso, delegue o recurso para um tipo que já faz RAII corretamente — como std::vector, std::string, ou (para um objeto único alocado dinamicamente) std::unique_ptr. Sua classe então não precisa escrever nenhum destrutor, nenhum construtor de cópia, nada — o compilador gera tudo automaticamente, e como cada campo já sabe se cuidar sozinho (é RAII também), a versão gerada automaticamente já está correta.

    Reescrevendo Buffer seguindo a regra do zero:

    class Buffer {
private:
    std::vector<int> dados_;   // vector ja e RAII -- ele mesmo aloca/libera

public:
    explicit Buffer(std::size_t tamanho) : dados_(tamanho, 0) {}

    void define(std::size_t indice, int valor) { dados_[indice] = valor; }
    int obtem(std::size_t indice) const { return dados_[indice]; }
    std::size_t tamanho() const { return dados_.size(); }

    // sem destrutor, sem construtor de copia -- e nao precisa!
};

Buffer a(10);
Buffer b = a;   // copia de verdade, profunda -- vector sabe se copiar corretamente

    Agora copiar b = a faz uma cópia de verdade do vector interno (cada um com seu próprio array por baixo), e não há double free nenhum: cada Buffer tem seu próprio vector, e cada vector sabe se destruir sozinho.

    std::unique_ptr: quando você precisa mesmo de um ponteiro¶

    Às vezes você precisa de um objeto único, alocado dinamicamente, sem container nenhum por cima (por exemplo, um objeto polimórfico, assunto do próximo capítulo). std::unique_ptr<T> é um "ponteiro inteligente" que segue RAII: ele dá delete automaticamente quando sai de escopo, e não pode ser copiado (só movido — fora do escopo deste curso, mas saiba que existe std::move para isso), o que impede exatamente o bug de double free descrito acima.

    #include <memory>

std::unique_ptr<Buffer> cria_buffer(std::size_t tamanho) {
    return std::make_unique<Buffer>(tamanho);
}

void usa() {
    auto b = cria_buffer(100);   // b e um unique_ptr<Buffer>
    b->define(0, 42);             // -> funciona como um ponteiro comum
}   // ~Buffer() roda automaticamente aqui, mesmo sem "delete" explicito em lugar nenhum

    std::make_unique<T>(argumentos...) cria o objeto e devolve o unique_ptr já apontando para ele — prefira essa forma a new direto.

    Erros comuns¶

    "double free or corruption" / crash no fim do programa — geralmente é o problema da cópia rasa descrito acima: uma classe com destrutor customizado que gerencia um ponteiro bruto, copiada sem construtor de cópia customizado. A correção é a regra do zero: troque o ponteiro bruto por vector/unique_ptr.

    Vazamento de memória silencioso (programa usa cada vez mais RAM) — um new sem delete correspondente em algum caminho do código (por exemplo, uma função que retorna cedo antes de chegar ao delete). A regra do zero elimina essa classe de bug inteira, porque não existe new/delete manual para esquecer.

    "error: use of deleted function" ao copiar algo com unique_ptr dentro — unique_ptr não pode ser copiado de propósito (só um dono por vez). Se sua classe tem um unique_ptr como campo, ela automaticamente também não pode ser copiada — isso é uma proteção, não um bug: pense se você realmente precisa copiar esse objeto, ou se uma referência/unique_ptr próprio resolve.

    Resumo¶

    • Destrutor (~NomeDaClasse()) roda automaticamente quando o objeto sai de escopo ou é destruído com delete — não importa o caminho de saída da função.
    • RAII: recurso adquirido no construtor, liberado no destrutor. vector, string, ofstream/ifstream já são RAII por baixo dos panos.
    • Copiar uma classe que gerencia um ponteiro bruto sem cuidado extra causa cópia rasa, e cedo ou tarde um double free.
    • Regra dos 3: destrutor customizado exige construtor de cópia e operador de atribuição customizados também.
    • Regra do zero (a recomendação deste curso): nunca gerencie recurso bruto diretamente — delegue para vector, string ou unique_ptr, e não escreva destrutor nenhum. O compilador gera a versão certa sozinho.
    • std::unique_ptr<T> + std::make_unique<T>(...): ponteiro inteligente com RAII, para quando você precisa mesmo de alocação dinâmica de um objeto único.
